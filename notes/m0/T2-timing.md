# T2 timing

- 我跑出来的数字（vsync 开，单位 ms）：

  | | CPU frame | CPU work | fence wait | GPU frame | Clear | Overlay |
  |---|---|---|---|---|---|---|
  | debug layer 开 | 17.555 | 0.987 | 13.037 | 0.086 | 0.056 | 0.030 |
  | debug layer 关 | 16.685 | 0.845 | 15.326 | 0.089 | 0.057 | 0.032 |

  关 vsync 的数字（CPU frame 约 1.3 ms）见 `T2-questions.md`。

- vsync 是什么，为什么跑基准测试要关掉：屏幕按固定节拍从上到下刷新（60Hz 就是每 16.67 ms 一次），开 vsync 就是等屏幕刷完一遍再换画面，这样不撕裂。但这样 CPU 帧时间会被锁在 16.67 ms，程序其实大部分时间在等屏幕，测不出真正的开销，所以基准测试要关。

- CPU 帧时间、CPU 工作时间、fence 等待，三者是什么关系：CPU 帧 ≈ CPU 干活 + 等 GPU（fence）+ 没打卡的部分（比如处理窗口消息）。开 vsync 时 fence 等待占了大头，CPU 只干了不到 1 ms 的活。

- GPU 时间戳为什么要 2 帧之后才能读：GPU 执行到那条命令才会写时间戳，比 CPU 录制晚很多。立刻读的话，可能读到 0（第一次），或者旧数据，甚至 GPU 写到一半的数据。要等这个帧槽位的 fence，避免冲突。2 帧在途，所以第 N 帧看到的是第 N−2 帧的时间，和 T1 back buffer 靠第 N−2 帧复原是同一个原因。

- 小实验 1：窗口拉大 / 缩小，Clear 的时间怎么变？拉的那一瞬间会变大，但是稳定下来，值就跟之前基本一致了。原来以为清屏要把每个像素写一遍，窗口越大越慢，结果不是。应该是 GPU 做了 fast clear：不真的写每个像素，只在元数据里记一笔"这块整块是这个颜色"。那一瞬间变大是因为改大小时要等 GPU 空闲、重建 back buffer。**测量比直觉可信。**

- 小实验 2：开 / 关 debug layer，CPU work 怎么变？只少了 0.14 ms（0.987 → 0.845），基本没变。因为 debug layer 的开销和 D3D12 调用次数成正比，现在每帧只调用几十次，没多少可检查的。和 DESIGN §5.2 "计时运行时关闭 debug layer" 有关。
  - 预测：T3 每个网格一次 draw call，每帧几百次调用，到时再对比，差距应该会变大。

- 意外发现：
  - debug layer 开的那次 CPU frame 是 17.555，不是 16.67。不是 debug layer 的锅：0.987 + 13.037 比 17.555 少了 3.5 ms，这段时间花在了没打卡的地方。我是点 × 关窗口的，按住标题栏按钮时 Windows 会卡住我们的循环，最近 60 帧正好把这一下算进去了。**人的操作会污染测量**，所以基准测试要固定路径、固定帧数（`--frames`）。
  - 我的输出里 `frames: 0`，帮 Claude 抓出一个从 T1 就有的 bug（`&&` 短路导致 `++frame` 没执行），已修。
