## 第 1 题：关掉 vsync 后，fence 等待为什么还有约 0.6 ms？这段时间 GPU 在干什么？

### 实测（`--no-vsync`，debug layer 开）

| CPU 帧 | CPU 工作 | fence 等待 | GPU 帧 | Clear | Overlay |
|---|---|---|---|---|---|
| 1.318 ms | 0.672 ms | 0.638 ms | 0.087 ms | 0.057 ms | 0.030 ms |

### 我的第一反应

fence 在等在途的两帧，GPU 这时在算之前的帧。

### 讨论

- 前半句对：fence 等的是**这个槽位上一次的那一帧**（第 N−2 帧）。
- 后半句算账就不对了：
  - GPU 执行我们一帧的命令列表只要 **0.087 ms**，两帧才 0.17 ms；CPU 准备一帧要 **0.67 ms**。
  - 如果 GPU 只干我们的活，CPU 回来时第 N−2 帧早就做完了，fence 等待应该 ≈ 0。
  - 实测 0.64 ms，说明 GPU 队列上每帧还有**我们没打卡的工作**：主要是 `Present` 本身（DXGI 的内部命令列表，T1 报错里出现过 `'Internal DXGI CommandList'`），可能还有 GPU 的调度、唤醒开销。我们在 `Present` **之后**才 `Signal` fence，所以 fence 也要等它做完。
- 再算一笔：CPU 工作 0.67 + fence 等待 0.64 ≈ **1.31 ms ≈ CPU 帧时间**。整条流水线按"GPU 队列每帧约 1.3 ms"的节拍在走，我们自己的工作只占 0.087 ms。

### 结论 / 教训

- **"GPU 帧时间"只量了我们自己的命令列表，看不见 `Present`。**
- 设计文档的经验法则"fence 等待高 → GPU 瓶颈"有前提：GPU 时间要覆盖 GPU 上的所有工作。GPU 时间很小的时候，瓶颈可能在测量范围之外。
- T3 有了 Sponza 之后，我们自己的 GPU 时间会变大，这块开销就不显眼了。
- 想直接看 `Present` 在 GPU 上的开销，要用 PIX 这类工具。

## 第 2 题：如果在 `endFrame` 之后立刻读时间戳，会读到什么？为什么必须等这个帧槽位的 fence？

### 我的第一反应

可能会读到 0；等 fence 可能是为了避免冲突。

### 讨论

两点都对。读到的**不是这一帧的数据**，具体看时机：

| 情况 | 读到什么 |
|---|---|
| 这个槽位第一次用 | **0**（新建的缓冲默认清零） |
| 之后的帧 | 这个槽位**上一次的旧数据**（第 N−2 帧的） |
| 最糟糕 | GPU **正写到一半**：开始时间是新的、结束时间是旧的，减出来是负数或特别大的数 |

- 原因：和 `ResourceBarrier` 一样，`EndQuery` / `ResolveQueryData` 只是**录进命令列表**，CPU 交出去的时候 GPU 还没执行。
- "避免冲突"就是关键：CPU 读的同时 GPU 可能正在写。**fence 是唯一能说"GPU 已经把这之前的事全部做完"的信号**，等到它，才保证拷贝完成、数据完整。
- 类比：TPU 上 GDMA 还在把结果搬进内存，不等 DMA 完成标志就去读，读到的要么是旧数据，要么是搬了一半的数据。

### 代码里怎么做的

- `src/profile/gpu_timer.h` 第 25～28 行的注释。
- 每个帧槽位有**自己的**读回区域，互不覆盖。
- 读数据放在 `GpuTimer::beginFrame` 里，而它在 `Device::beginFrame`（等这个槽位的 fence）**之后**调用（`src/app/main.cpp`）。所以第 N 帧显示的是第 N−2 帧的计时。
- 和 T1 对照：back buffer 的状态靠"第 N−2 帧的复原"，这里的时间戳是"第 N−2 帧写下的"。背后都是同一个原因：**2 帧在途**。

### 讨论中澄清的误会

| 我原来以为 | 实际上 |
|---|---|
| 关掉 vsync 后 fence 在等 GPU 算前面的帧 | 我们的帧 GPU 早就算完了；fence 在等的主要是 `Present` 这些**没打卡的**工作 |
| 立刻读只会读到 0 | 只有第一次是 0；之后是旧数据，甚至新旧混在一起 |
