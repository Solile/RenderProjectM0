## 第 1 题：back buffer 一开始为什么处于 PRESENT？是谁把它放进去的？

### 结论

- **第 1 帧：** back buffer 是 **交换链（DXGI）** 创建的，不是我们。创建交换链（`CreateSwapChainForHwnd`，`BufferCount = 2`）时，DXGI 顺便建好了 2 个 back buffer，并且直接放在 PRESENT 状态（它们一出生就归显示系统管）。我们的代码没有机会指定初始状态。
- **之后每一帧：** 靠 **这个 buffer 上一次被使用那一帧** 结尾的 barrier ②（`recordBackBufferToPresent`）把它 **复原** 成 PRESENT。2 个 buffer 轮流用，所以第 N 帧靠的是第 **N−2** 帧的复原（3 个 buffer 就是 N−3）。

### 时间线

```
帧1  用 buffer A： [PRESENT] ─①→ [RENDER_TARGET] 清屏 ─②→ [PRESENT]  Present(A)
帧2  用 buffer B： [PRESENT] ─①→ [RENDER_TARGET] 清屏 ─②→ [PRESENT]  Present(B)
帧3  又用 buffer A：[PRESENT] ─①→ ...   ← 这个 PRESENT 是帧1 的 ② 复原的
```

### 讨论中澄清的误会

| 我原来以为 | 实际上 |
|---|---|
| `ComPtr<ID3D12Resource> backBuffers_[2];` 就把 buffer 建好了 | 只是 2 个**空指针**（空通讯录），没分配任何显存 |
| `GetBuffer` 创建了 buffer | 是 **Get** 不是 Create：向交换链要它已有的第 i 个 buffer 的地址 |
| `cmd` 是"device 的第一帧" | `cmd` 是**每帧**重置后重复使用的命令列表 |
| 每帧只做一次切换，方向轮流变（帧1 引擎→画布，帧2 画布→引擎……） | **每帧两个 barrier 都做**（都在 `main.cpp` 的 `while` 循环里）。轮流的是 **buffer A / B**，不是方向 |

### 核心收获

- **资源状态会一直保持，D3D12 不会在每帧开头帮你重置。**
- **`StateBefore` 是一个承诺**：根据"之前做过什么"告诉 GPU 资源现在的状态。barrier ① 写 `StateBefore = PRESENT` 之所以对，全靠上一次的 barrier ② 把它复原了。漏了 ②，① 的承诺就成了谎话。
- debug layer 报错里的 `Expected ... Actual ...`，就是在对比"你的承诺"和"它自己追踪到的真实状态"。
- 对比 T3：到时用 `CreateCommittedResource` 自己创建贴图 / 顶点缓冲，它有个参数叫 `InitialState`，初始状态由自己选。

### 代码位置

- `src/rhi/device.cpp`：`CreateSwapChainForHwnd`（创建交换链和 back buffer）、`createBackBufferViews` 里的 `GetBuffer`（取地址）
- `src/app/main.cpp`：`while` 循环里的两个 barrier 调用

## 第 2 题：subresource 是什么？back buffer 有几个？

### 概念

一个纹理资源可以由几种"子块"组成，每个 **（第几层 mip，第几个数组切片，第几个 plane）** 组合就是一个 subresource，有自己的编号，**可以单独切换状态**。

| 维度 | 是什么 | 例子 |
|---|---|---|
| mip 层级 | 同一张图的缩小版本，每层宽高减半 | mip 0 = 原尺寸（最大），1 = 1/2，2 = 1/4…… |
| 数组切片 | 几张同尺寸的图放在一个资源里 | 立方体贴图 6 个面 |
| plane | 同一张图按分量分开存 | NV12：Y 平面 + UV 平面 |

### 结论

- **back buffer 有 1 个 subresource，编号是 0。** 1 层 mip × 1 个切片 × 1 个 plane（`R8G8B8A8` 是交错格式）= 1。
- 报错里的 `(subresource: 0)` 是**编号**，不是数量。
- **报错本身看不出一共几个**：它只提到出事的那一个。想知道全貌要问资源本身：`resource->GetDesc()` 里的 `MipLevels`、`DepthOrArraySize`。

### `0` 和 `ALL_SUBRESOURCES`

- `D3D12_RESOURCE_BARRIER_ALL_SUBRESOURCES = 0xffffffff`：不是"很多个"，而是**哨兵值**（32 位最大值），真实编号永远到不了，所以不会和编号 0 撞车。思路同 `std::string::npos`。
- "不交接"不是靠填数值表达的：**不想交接就不调用 `ResourceBarrier`**。`Subresource` 只有两种填法：具体编号，或 `ALL`。
- **在 back buffer 上：** `0` 和 `ALL` 效果完全一样（只有一个 subresource）。
- **在多层 mip 的贴图上（T3）：** 写 `0` 只切 mip 0，其他层停在旧状态（比如 `COPY_DEST`）。远处物体采样小 mip 时：有 debug layer 会报错；没有就是**未定义行为**（可能 Intel 上正常、NVIDIA 上花屏）。
- 所以默认写 `ALL`：表达"整块资源都切"的意图，代码以后用到多层贴图上也不出错。

### 什么时候按编号切？

同一个资源的不同部分**同时**被不同方式使用。经典例子：**生成 mip 链**，读第 i−1 层（SHADER_RESOURCE）画出第 i 层（RENDER_TARGET），只能一层一层按编号切。

### 讨论中澄清的误会

| 我原来以为 | 实际上 |
|---|---|
| `(subresource: 0)` 表示 0 个 / 没交接 | 是**编号 0**，像 `arr[0]` |
| 写 `0` 就是"不交接" | 写 `0` 是"交接编号 0 那一个"；不交接 = 不调用 |
| `0xffffffff` 表示很多个 | 是哨兵值，表示"全部" |

## 第 3 题：D3D11 不用写 barrier，D3D12 为什么要你手写？代价和好处？

### D3D11 驱动是怎么"自动"做的

- 每次 draw 之前，驱动要决定："这次用到的资源上次是怎么用的？要不要先插一次交接（刷 cache、解压缩）？"
- 这本账在 **CPU** 上记：命令是在 CPU 上组装好再交给 GPU 的，要不要插交接必须在组装时决定，GPU 只照着执行。
- **每次 draw 都要查**所有绑定的资源，几千次 draw 就查几千遍，这就是 D3D11 有名的 **draw call 开销**。
- 记账的目的是**做决定**，不是记日志。
- debug layer 在背后做的也是同样的记账（目的是检查你），所以它有 CPU 开销，计时运行时要关掉（DESIGN §5.2）。

### 为什么多线程录制时驱动没法自动做

- GPU 执行确实有严格顺序，但顺序是在**提交**（`ExecuteCommandLists`）时由应用决定的，和线程编号无关。
- **录制时顺序还没定**：列表 5 里某张贴图的"之前状态"取决于列表 1～4，而它们正在别的线程上同时录，最终谁排前面也不知道。一个命令列表还可能被提交多次，或者一次都不提交。
- 驱动只剩两条路：让线程排队录（没了并行），或者提交时再补算（单线程，开销又回来了）。
- D3D12 的选择：**应用最清楚整帧的结构，由应用来声明。**

```
录制（8 个线程同时进行）          提交（之后，应用决定顺序）
线程1 录 列表1 ─┐
线程2 录 列表2 ─┤                 ExecuteCommandLists(列表3, 列表1, 列表2 …)
   …            ├──────────▶
线程8 录 列表8 ─┘
```

### 类比

| | 谁负责插同步 | 什么时候决定 |
|---|---|---|
| D3D11 驱动 | 驱动 | 运行时，每次 draw 现场检查 |
| D3D12 | 应用 | 提前，应用知道整帧要做什么 |
| TPU 工作 | 编译器 / 运行时 | 编译时，看得到整张计算图 |

### 好处

- 省掉驱动每次 draw 的记账，CPU 开销下降。
- 命令列表可以多线程并行录制。
- 开发者知道真实需求，可以只在需要的地方交接，控制力更强。

### 代价：对开发者要求变高

| 错误类型 | 例子 | 后果 |
|---|---|---|
| 少写 / 写错（正确性 bug） | 漏了 barrier ②、`StateBefore` 填错 | 有 debug layer 会报错；**没有就不报错**，结果未定义：花屏、闪烁、设备丢失 |
| 多写 / 写太宽（性能 bug） | 不需要时也插 barrier，状态给太宽 | 画面正确但 GPU 白白停下来刷 cache 等待，**变慢了也不知道为什么** |

- 要求是**不多也不少**。
- 写错的后果**可能和显卡有关**：Intel 上碰巧正常，NVIDIA 上出问题。所以不能靠肉眼，要靠 debug layer。

### 讨论中澄清的误会

| 我原来以为 | 实际上 |
|---|---|
| 驱动记账是为了方便查日志 | 是为了**每次 draw 前决定要不要插交接** |
| 并行录制时，按序号先执行就行 | 执行顺序在**提交时**才定，录制时谁先谁后还不知道 |

## 第 4 题：`PRESENT` 和 `COMMON` 的数值？为什么一个值有两个名字？

### 数值

```cpp
D3D12_RESOURCE_STATE_COMMON  = 0,     // d3d12.h 第 1762 行
D3D12_RESOURCE_STATE_PRESENT = 0x0,   // d3d12.h 第 1781 行
```

**是同一个数。** 进制只是**人的写法**，编译器会全部换算成二进制，内存里都是 32 个 0 bit：

```
0    →  00000000 00000000 00000000 00000000
0x0  →  00000000 00000000 00000000 00000000
```

（`10` 和 `0xA` 也一样，存的都是 `1010`。）头文件一个写 `0` 一个写 `0x0`，只是书写习惯：后面的状态值（`0x4`、`0x8`……）按 bit 位设计，所以用十六进制。

证据：

- debug layer 报错写的是 `0x0: D3D12_RESOURCE_STATE_[COMMON|PRESENT]`：它只拿到一个数，分不清是哪个名字，只好都列出来。
- `static_assert(D3D12_RESOURCE_STATE_PRESENT == D3D12_RESOURCE_STATE_COMMON);` 能编译通过（编译时检查，不成立就编译失败）。

### 为什么要两个名字

- 名字是写给**人**看的，而且是在**源代码**里，不是在报错里（报错里两个名字一起出现，帮不上忙）。
- **同一个值，表达不同的意图：**
  - barrier ② 写 `PRESENT`：画完了，交还给显示系统去呈现。
  - 写 `COMMON`：机器上完全一样，但读的人会以为"切到通用状态，是要给别的队列用？"
- 微软文档对 `PRESENT` 的说明："Synonymous with `D3D12_RESOURCE_STATE_COMMON`"（同义词）。
- 类比：`#define WARMUP_FRAMES 120` 和 `#define MAX_BATCH 120` 值相同，但绝不能混用；哪天一个改成 200，另一个不该跟着变。**名字承载含义，不是数值。**

### 讨论中澄清的误会

| 我原来以为 | 实际上 |
|---|---|
| `0x0` 和 `0` 对机器来说尺度不一样 | 进制只是写法，存下来的二进制完全相同 |
| 两个名字是为了报错时看出是哪个状态 | 报错只看得到数值；名字是为了让**源代码**表达意图 |
